# بروتوكول فحص وإصلاح مَدخَل

## المرحلة A — تحديد المشكلة
1. صياغة المشكلة في جملة واحدة.
2. تحديد المسار المتأثر: UI / profile / matching / evaluation / applications / subscription / jobs / employer.
3. تحديد ما هو المتوقع وما هو الواقع.

## المرحلة B — جمع الأدلة
1. قراءة الملفات ذات الصلة.
2. قراءة schema والجداول ذات الصلة.
3. فحص الدوال والـEdge Functions عند الحاجة.
4. فحص السجلات عند وجود خطأ تشغيلي.
5. عدم تغيير أي شيء.

## المرحلة C — تشخيص
إنتاج تقرير:
- السبب المحتمل.
- الدليل.
- درجة الثقة.
- الملفات المتأثرة.
- الجداول المتأثرة.
- الأنظمة التي لن تُلمس.

## المرحلة D — اقتراح
اقتراح أصغر تعديل يحقق الهدف.
إذا كان التغيير كبيرًا، تقسيمه إلى خطوات صغيرة.

## المرحلة E — الموافقة
في المستوى الحالي لا تنفيذ للكتابة.
يُعرض:
- ماذا سيتغير؟
- أين؟
- لماذا؟
- المخاطر؟
- طريقة التراجع؟

## المرحلة F — التنفيذ لاحقًا
بعد فتح صلاحية مناسبة:
1. إنشاء فرع.
2. تطبيق التغيير على الفرع.
3. اختبار.
4. مراجعة الفرق.
5. إنشاء Pull Request.
6. عدم الدمج تلقائيًا.

## المرحلة G — التحقق
اختبار الوظيفة التي أصلحت، ثم اختبار عدم تأثر المسارات القريبة.

## المرحلة H — السجل
تسجيل:
التاريخ، المشكلة، السبب، التغيير، الاختبارات، النتيجة، commit/PR، والموافقة البشرية.

## قاعدة الفشل
إذا فشل الاختبار أو ظهر أثر جانبي غير متوقع: إيقاف التغيير، عدم الاستمرار في الترقيع، وإرجاع الحالة الآمنة.
