# خريطة تدفق مَدخَل — 2026-09-27

هذه خريطة تشخيصية مبنية على المسار النشط في `main`. لا تنفذ أي تعديل إنتاجي.

## 1) الباحث عن عمل

### الدخول
`openWorker()`
→ `workerScreen`

### إنشاء/تعديل الملف
`openProfile()`
→ `profileScreen`
→ `loadProfile()`

الحقول الحالية تشمل:
- الاسم الأول
- اسم الأب
- اسم العائلة
- اسم الأم
- تاريخ الميلاد
- المؤهل
- المهنة المعتمدة
- المكان
- نوع العمل
- سنوات الخبرة
- مهارات إضافية
- النبذة المهنية

### اختيار المهنة
`searchOccupations()`
→ RPC: `search_madkhal_occupations`
→ فلترة المهن وفق وجودها في نص فرص مَدخَل
→ اختيار `occupation_uri` و`occupation_label`
→ `loadOccupationSkills()`
→ RPC: `get_madkhal_occupation_skills`

### الحفظ والتأكيد
`saveWorker()`
→ يتحقق من: الاسم + اسم الأم + المهنة + المكان
→ يبني ملفًا موحدًا
→ يحفظ نسخة محلية في LocalStorage
→ يحسب التقييم الفوري/المهني
→ يحصل على جلسة Supabase
→ Upsert إلى `worker_profiles`
→ RPC: `process_my_worker_matches`
→ يحدّث `profiles`
→ Upsert إلى `job_preferences`
→ يحفظ تقييمات المهارات في `worker_skill_assessments`
→ يفتح الحساب بعد نجاح المسار.

### التقييم
يوجد مساران:
- تقييم فوري محلي لا يعلّق الواجهة.
- تقييم متقدم مرتبط بمهارات المهنة مع مهلة زمنية.

العوامل الحالية:
- اكتمال الملف 10%
- ملاءمة المهنة 20%
- مهارات المهنة 35%
- الخبرة 20%
- المؤهل 10%
- النبذة 5%

### الفرص
`openOpportunities()`
→ `loadJobs()`
→ قراءة `public.jobs` للحالات active
→ فلترة سوريا/الشرق الأوسط
→ إزالة التكرار بالـ canonical/source URL أو id
→ `renderOpportunities()`
→ `matchScore()` لترتيب النتائج.

### تفاصيل الفرصة
`openJobDetails()`
→ يعرض التفاصيل
→ يوضح أن التقديم من المصدر الأصلي
→ زر `applyToCurrentJob()`

### التقديم
`applyToCurrentJob()`
→ يتأكد من الملف والمهنة والجلسة
→ يقرأ `worker_profiles`
→ يسجل في `madkhal_applications`
→ يسجل نسخة محلية للمتابعة
→ يفتح `source_url/canonical_url`
→ يعرض الطلب في الحساب.

## 2) الاشتراك

### المسار
`openSubscription()`
→ `subscriptionScreen`
→ `startSubscriptionRequest()`

الحالة تحفظ محليًا، ثم عند وجود مستخدم:
→ `profiles`
→ `subscriptions` مع:
- plan = monthly
- audience = worker
- status = requested
- price_usd = 1
- currency = USD
- auto_renew = false
- provider

يوجد أيضًا مسار `startLocalPayment()` يسجل طلب الدفع بعد اختيار وسيلة دفع.

### ملاحظة تشخيصية
ملفات الدفع/الاشتراك الإضافية الموجودة في المستودع ليست جزءًا من التحميل المباشر الحالي، لذلك لا تُعتبر مصدر التحكم النهائي قبل إثبات تحميلها.

## 3) المطابقة

### مطابقة الفرص المنشورة
داخل الصفحة:
`matchScore()`
→ مطابقة مهنية + مهارات + موقع + نوع عمل + خبرة + تقييم.

يوجد تشدد خاص في:
- الطب
- الطب الشرعي
- الأمن
- المحاسبة
- الهندسة
- التعليم وتخصصاته.

### مركز المطابقة المباشر
`worker-match-lifecycle.js`
→ `process_my_worker_matches`
→ `create_worker_match_notifications`
→ `get_my_worker_matches`

الحالات المرصودة:
`employer_interested`
→ `accepted` أو `declined`
→ `contact_opened`
→ `interview`
→ `offer`
→ `hired`
مع حالات إغلاق إضافية في منطق المسار.

## 4) صاحب الفرصة

المسار النشط:
`employer-flow-enhancement.js`

عند تحميل الصفحة:
- يضيف رقم التواصل.
- يحول اختيار المهنة إلى قائمة مهن معيارية.
- يستدعي `search_madkhal_occupations`.

عند النشر:
`submitEmployerVacancyEnhanced()`
→ يتحقق من البيانات + الهاتف
→ `profiles` بدور employer
→ `employer_vacancies`
→ confirmation_at / confirmation_version
→ يحول الحالة إلى matching
→ RPC: `process_my_employer_matches`
→ يقرأ عدد `match_requests`
→ يبقي الفرصة `private_match_only`.

هذا يتوافق مبدئيًا مع دستور V2: فرصة خاصة للمطابقة وليس قائمة عامة.

## 6) الإشعارات

هناك مستويان:
- LocalStorage للتنبيهات الفورية/الاحتياطية.
- جدول `notifications` للمستخدم المسجل.

المطابقة المباشرة تضيف إشعارات عبر RPC أيضًا.

## 7) أهم نقاط الخطر التشخيصية

1. `index.html` يحمل كمية كبيرة من المنطق، لذلك تعديل صغير فيه قد يؤثر على عدة مسارات.
2. يوجد تاريخ من ملفات الإصلاح الخارجية غير المحملة مباشرة.
3. توجد نسخ محلية ونسخ Supabase لبعض الحالات؛ يجب معرفة مصدر الحقيقة قبل تغيير أي حالة.
4. التقييم لديه مسار فوري ومسار متقدم؛ حذف أحدهما قد يعيد مشكلة التعليق التي عولجت سابقًا.
5. التقديم الخارجي يسجل الطلب داخليًا قبل فتح المصدر؛ لا ينبغي تغيير الترتيب دون اختبار.
6. الاشتراك يسجل `requested` ولا يعني أن الدفع تحقق أو أن الاشتراك أصبح `active`.
7. قاعدة Supabase نفسها مشتركة مع نظام المطعم؛ أي SQL إصلاحي يجب أن يتأكد من نطاقه على جداول مَدخَل فقط.

## 8) قاعدة الوكيل بعد هذه المرحلة

لا يبدأ الوكيل إصلاحًا بمجرد رؤية ملف يحمل كلمة `fix`.

قبل أي تعديل يجب تحديد:
**الشاشة → الدالة → مصدر البيانات → الجدول/RPC → حالة البيانات → المستهلك التالي.**

ثم يختار أصغر نقطة إصلاح قابلة للعكس والاختبار.
